system, `direct_routes`, `scrape_sources`, `advisor_notes`, a Playwright→Cheerio→LLM→Zod

the repo.** No migration creates any of these tables; no `src/scraper/` or `src/ingestion/`
equivalent exists anywhere.

What actually exists is much smaller: `destination_facts` and `property_facts` tables
(migration 010), each just `{destination/property_name, dining_recs, activities/notes}`,
manually populated — no trust tiers, no scraper, no ingestion pipeline. Migration 010's own
comment calls these "KB tables," distinct from Trainer Chat's separate `client_documents` /
`knowledge_chunks` KB (migrations 008–009, unrelated to this Sheet section entirely).

This is the biggest gap between Sheet and repo. Two explanations, and it matters which:
1. The elaborate schema was built by hand directly in Supabase, never captured as a
   migration (violates the not-yet-resolved authoritativeness convention in row 71).
2. The Sheet describes a spec that was scoped down to `destination_facts`/`property_facts`
   during actual build, and the Sheet rows were never updated to reflect the descope.

I can't tell which from the repo alone — worth a direct check against the live Supabase
schema before trusting any "Done" status in this section.
